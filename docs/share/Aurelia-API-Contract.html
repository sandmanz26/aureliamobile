0 · Summary

  • One REST API, https://api.aurelia.care/v1, JSON over HTTPS. It serves both clients: the React web app, which is the reference, and the Flutter app. The same contract serves prod v1 and prod v2; the design version is a client concern, so the API returns everything both need (§2.4).

  • The core loop is the API's first job:

    1. sign in;
    2. onboarding;
    3. a conversation with Aurelia;
    4. proposals with reasons;
    5. a build (async, streamed progress);
    6. play;
    7. check-in;
    8. the next chapter and a reminder;
    9. progress told in words.

    Community, coins, challenges and admin come after it (§10).

  • AI features run server-side only. Clients never hold a model key. Six AI capabilities sit behind the API (§8):

    • understanding the first sentence;
    • the cockpit conversation;
    • change proposals with a "Why";
    • the session build (script → voice → sound → visuals);
    • the next-chapter plan;
    • progress summaries in words.

    A safety layer runs on every user turn.

  • Honesty is part of the contract, not a UI choice. No figure that is not the person's own, or that nobody measured, may be returned to a client without a provenance field. Rule A5.1 in docs/HANDOFF.md.

2 · Decisions this contract makes

The open product decisions are listed in §11. These are the ones the contract takes so engineering is not blocked. Each can be reversed before build.

  1. Persistent accounts (D2 = yes). Sign-in persists via a refresh token. The journey, journal, check-ins, onboarding and conversations move from localStorage to the account. Without this no retention number can be measured (J039 F9).
  2. Free plan limits builds, not messages (logic-review decision 1). The server owns the counter: N builds per account per day, reset at local midnight. Conversation is unlimited, and the first build is never counted (U050). The client renders entitlements and never computes the limit.
  3. One version model (decision 3). A session owns an ordered list of versions: v1.0 for the first build, +0.1 per build. A fork is a new session at v1.0 that records parent {sessionId, versionId}. Live changes only on (Re)publish, and publish is refused while a build runs (decision 4, logic B3).
  4. The API serves both design versions from one shape. Example: a proposal carries both estimate (nullable, with provenance) and basis (the reasons). Prod v1 renders the estimate; prod v2 renders the basis. The server sets estimate to null until an estimate is measured (A5.1), and prod v1 then hides the chip. No endpoint branches on design version. The client sends X-Aurelia-UI: 4|5 only for analytics.
  5. Numbers are integers; formatting is the client's. plays: 18500, not "18.5k". Both clients use one formatting rule (docs/FOR-BACKEND.md §1.1, now decided): ≥1000 → one decimal + k, ≥1,000,000 → one decimal + M, trailing ".0" dropped.
  6. Outcomes always carry provenance. Any Outcome has {label, value, unit, provenance: "self_reported"|"measured"|"sample", n, window}. Sample data is never returned in production responses after launch.
  7. One conversation per session (decision 9). A session's conversation is reopened with it. A Home ask opens a new conversation. Hand-offs carry source (logic D1, D2).
  8. Builds run server-side, independent of the screen (logic D3), as jobs with streamed progress. The client may leave and come back.
  9. The safety layer is mandatory on every user-authored text input (messages, journal, check-in notes, publish titles). It runs before generation (logic H1; A5.10).
  10. Privacy by default.
    • Signal sources start off.
    • Consent is stored per source, with the consent-text version.
    • Journal and check-in notes are private and are used for generation only with the personalisation consent.
    • Publishing shares title, sound, visuals and script, never check-ins, journal, wearable data or the conversation (the prod v2 privacy note is the contract).

3 · Conventions

3.1 Transport and versioning

  • Base URL https://api.aurelia.care/v1. Staging: https://api.staging.aurelia.care/v1.
  • JSON (application/json; charset=utf-8). Timestamps in RFC 3339 UTC (2026-11-10T09:00:00Z). Durations in seconds. Ids are opaque strings with a type prefix (usr_, ses_, ver_, cnv_, msg_, bld_, jrn_, chk_, jnl_, prp_, chl_, ntf_). URLs use slugs for public sessions (/sessions/{slugOrId}) because the web routes already do (/play/{slug}).
  • Breaking changes go to /v2. Additive changes (new fields, new enum values) are not breaking: clients must ignore unknown fields and treat unknown enum values as "other". The web client already validates every response with Zod (requestJson). Schemas use .passthrough()-style tolerance for this reason.
  • Aurelia-Client: web/0.1.0+bc028a6 or ios/… on every request (support and telemetry). X-Aurelia-UI: 4|5 (design version, analytics only).

3.2 Authentication

  • Authorization: Bearer <access token>: a JWT, 15-minute lifetime. The refresh token is opaque, rotates, lives 30 days rolling (decision 14), and is stored in an httpOnly cookie on web and in secure storage on mobile.
  • OAuth providers: Google (live in UI), Apple (required for iOS once Google is offered). The exchange runs server-side. Sign-up and sign-in share POST /auth/oauth/{provider}.
  • Password reset never reveals whether an address exists (PRD rule). It always returns 202.
  • Public endpoints (catalogue, preview playback, challenges list) accept no token. Personalised fields are then simply absent.

3.3 Errors (RFC 9457 problem details)

{
  "type": "https://api.aurelia.care/problems/build-limit-reached",
  "title": "Daily build limit reached",
  "status": 429,
  "code": "build_limit_reached",
  "detail": "You have used 5 of 5 builds today.",
  "retryable": false,
  "resetAt": "2026-11-11T00:00:00+07:00",
  "requestId": "req_01J…"
}

code is the stable, machine-readable key; clients switch on it, never on title. retryable matches the client's existing HttpError.retryable (408/429/5xx/network). Standard codes:

HTTP code When
400 invalid_request Schema violation (with errors[] of {path, message})
401 unauthenticated Missing or expired token
403 forbidden Authenticated but not allowed (e.g. editing someone else's session: logic G2)
404 not_found Also returned for private resources you cannot see (no existence leak)
409 conflict / build_in_progress / version_mismatch Publish while building; stale If-Match
422 unsafe_content The safety layer blocked user content (§8.7); the body carries support resources
422 consent_required The action needs a consent the user has not given
429 rate_limited / build_limit_reached Retry-After header; resetAt for plan limits
503 ai_unavailable Model or vendor outage; retryable: true

3.4 Pagination, filtering, idempotency, concurrency

  • Cursor pagination: ?limit=20&cursor=… → { "data": [...], "nextCursor": "…" | null }. limit ≤ 100.
  • Idempotency: every POST that creates or costs something (messages, builds, check-ins, publish, recreate, payments) requires Idempotency-Key: <uuid>. A replay returns the first result for 24 h. Mobile networks drop responses, and a double build costs money and a version number.
  • Optimistic concurrency: mutable documents return ETag. Writes send If-Match; a mismatch is 409 version_mismatch.
  • Rate limits per token: 60 req/min general, 20 messages/min, 10 builds/hour. Headers RateLimit-Limit, RateLimit-Remaining, RateLimit-Reset.

3.5 Streaming

Two endpoints stream, with Server-Sent Events (text/event-stream):

  • the assistant's reply to a message (§5.4);
  • a build's progress (§5.6).

SSE was chosen over WebSockets because it works through the PWA service worker rule (/api is never cached), proxies and Vercel, and it reconnects with Last-Event-ID. Every stream ends with a terminal event (message.completed / build.completed / error). A client that loses the stream fetches the resource by id; streams are a convenience, the resource is the truth.

3.6 Webhooks (outbound, later phases)

These are for partners and internal workers, not clients: build.completed, checkin.created, safety.flagged, subscription.updated. They are signed (Aurelia-Signature: t=…,v1=HMAC-SHA256) and retried with backoff for 24 h.

4 · Data model

Field names are camelCase on the wire. Shapes are what the clients model today (src/lib/*, src/chat/*, docs/FOR-BACKEND.md §1), corrected by §2. ? = optional or nullable.

User {
  id, email, displayName, photoUrl?, createdAt,

4.2 Sessions, versions, lineage

4.4 Proposals ("Change this session": one list, with Why)

ProposalSet {
  id, conversationId, sessionId?, createdAt,
  sections: [
    { kind: "suggested",  title: "Aurelia suggests",  options: ChangeOption[] },  // preselected
    { kind: "diagnosis",  title: "Based on your diagnosis", options: ChangeOption[] },
    { kind: "experiment", title: "Experiments", options: ChangeOption[] }
  ]
}

ChangeOption {
  id, title,                              // ≤ 13 chars for the folded deck (U050)
  description,                            // "What it does"
  kind: "visual" | "sound" | "movement" | "voice" | "script" | "length",  // the sheet filter
  channel?: "audio" | "visuals",
  preselected: bool,
  isExperiment: bool,                     // untested: v2 says so; no estimate ever
  estimate?: { value: number, unit: "percent", provenance, n } | null,  // prod v1 chip; null until measured
  basis: {                                // prod v2 "Based on: …"
    goal?: string, lastCheckIn?: { mood: 1..5, label }, wearable?: string,
    words?: string, sessionHistory?: bool, text: string   // text = ready-to-render sentence
  },
  previewSessionSlug?                     // the audio sample the card plays
}

The server writes basis.text as a sentence, so both clients render the same words, e.g. "your goal (“Sleep better”) and your wearable." It is joined as a list (the U057 bug must not reappear).

4.6 Journey, check-ins, journal, progress

Journey {                                   // the five-chapter loop (U050)
  id, goal, name: "Sleep better", sessionId, chapterTarget: 5,
  chapters: [{ number, versionId?, unlockedAt, playedAt?, checkInId? }],
  reminder?: { time: "22:30", timezone, channel: "calendar" | "push" | "email", enabled }

CheckIn {
  id, journeyId?, sessionId, versionId, chapter?,

}
// The response to POST check-in also carries the next-chapter plan:
NextChapterPlan { chapter: 2, unlocksAt, headline: "Chapter 2 is ready tomorrow night",
                  plan: "Chapter 2 keeps what worked and goes a little deeper.",
                  changes: ChangeRef[], reminderSuggestion: { time: "22:30" } }

JournalNote { id, text (≤ 500), mood?: 1..5, createdAt }     // private; prod v2

ProgressSummary {                           // prod v2 "Progress in words"
  goal, chaptersDone, chapterTarget,
  trend: "up" | "same" | "down" | "new",   // rule in lib/journey feelingSummary: halves, ±0.5
  usual?: "Pleasant",
  headline: "After one chapter you felt pleasant.",
  detail: "Aurelia needs two check-ins before it can say which way things are going.",
  basis: "Based on: 1 check-in after your chapters, and your Apple Watch (example data…)",

Report { id, period: { from, to }, headline, body, highlights[], generatedAt }  // the two-week report

The trend and usual rules are deterministic and defined server-side exactly as feelingSummary(). The AI writes only the words around them (§8.5), never the direction.

8 · The AI system

8.1 Principles

  1. Server-side only, one gateway. Every model call goes through an internal ai-gateway service. It owns the policies, the safety layer, caching, retries, fallbacks, logging and cost. No client and no other service calls a model directly.
  2. Structured where it drives the product, free text where it is talked to people. Anything the app acts on (intent, proposals, a session spec, a plan) is returned as schema-validated JSON (structured outputs). Only the words people read are free text.
  3. Deterministic decisions stay in code. Free-limit counting, version numbers, the progress trend, qualified plays, reminder times and the WHO-5 thresholds (later) are code, not model judgement. The model explains them; it does not decide them.
  4. Nothing invented about the person. The model is given only the person's own data. Prompts forbid claims about effects, scores or numbers not present in the input. Outputs are checked by a validator that rejects any number not traceable to the input (A5.1).
  5. Every AI output names its basis. basis on proposals; basis on progress summaries. It is the prod v2 "Why", and it doubles as an audit trail.

Each route is one policy in /admin/ai/policies: a versioned system prompt, model, effort, schema and limits.

8.3 Model and request settings

The AI provider is Anthropic (Claude) via the Anthropic API, using the official TypeScript SDK (@anthropic-ai/sdk), matching the stack.

  • Model: claude-opus-5-5 for every route. Thinking is always on with this model, and depth is set per route with output_config.effort. The default is medium, so always set it explicitly: low for intent.infer, safety.classify and progress.words; medium for cockpit.reply, proposals.generate and chapter.plan; high for session.spec and session.script.
    • Whether some high-volume routes (intent.infer, safety.classify) move to a cheaper model is a cost decision for the product owner (§11), made only after an eval shows quality holds.
    • The model id is a policy field, so the change needs no deploy.
  • Structured outputs: routes with a schema use the SDK's client.messages.parse() with output_config.format (Zod schemas shared with the API's own response schemas). Tool calls in cockpit.reply use strict: true tools with tool_choice: auto; forced tool choice is not supported on this model.
  • Streaming: cockpit.reply streams (client.messages.stream). The gateway re-emits text deltas as the SSE message.delta events in §5.4.
  • Prompt caching: the system policy and the allowed-change catalogue go first and stay byte-stable, with cache_control on the stable prefix. The person's data and the conversation come after it. Volatile values (timestamps, request ids) never go in the system prompt. Monitor usage.cache_read_input_tokens.
  • Refusals and fallbacks: check stop_reason before reading content. A refusal is mapped to a safe, scripted reply, never a blank screen (logic D6). Server-side refusal fallbacks are enabled (fallbacks: "default" under the server-side-fallback-2026-07-01 beta). Fallback events are logged to AI monitoring.
  • Retries: the SDK retries 408/409/429/5xx twice. The gateway adds a circuit breaker and maps exhaustion to 503 ai_unavailable with retryable: true.
  • Data: journal and notes are sent only with personalisation consent. Names are not needed and not sent. Data residency and zero-retention terms are a decision (§11).

Illustrative gateway call for proposals.generate (SDK pattern as documented; verify against the installed SDK when implementing):

import Anthropic from "@anthropic-ai/sdk";
import { zodOutputFormat } from "@anthropic-ai/sdk/helpers/zod";
import { ProposalSetSchema } from "@aurelia/contract"; // the same Zod schema the API returns

const client = new Anthropic();

const response = await client.messages.parse({
  model: "claude-opus-5-5",
  max_tokens: 16000,
  system: [{ type: "text", text: policy.systemPrompt, cache_control: { type: "ephemeral" } }],
  messages: [{ role: "user", content: renderProposalInput(context) }],
  output_config: { effort: "medium", format: zodOutputFormat(ProposalSetSchema) },
});

if (response.stop_reason === "refusal" || !response.parsed_output) {
  return scriptedFallbackProposals(context); // never an empty sheet
}
return validateAgainstCatalogue(response.parsed_output, allowedChanges);

8.4 SessionSpec and the build pipeline

The model never produces audio. It produces a spec, and the build pipeline renders it.

SessionSpec {
  goal, lengthSec, voice: { gender: "female"|"male"|"none", pace: 0.6..1.2 },
  sound: { bed: "nature"|"music"|"frequencies"|"silence", layers: [{id, level 0..100}], tuningHz? },
  visuals: { palette: [hex], movement: 0..1, form: "orb"|"waves"|… },
  breath?: { inhaleSec, exhaleSec },
  chapters: [{ label, startSec, endSec, intent }],
  constraints: { excluded: ["frequencies", "spiritual_language", …] }   // the person's "no …"
}

Pipeline stages (the Build.stage values): plan (session.spec) → script (session.script) → voice (TTS vendor) → sound (sound-bed and layer rendering, vendor or library) → visuals (parameters; generated imagery later) → mix (loudness-normalised master, HLS + MP3) → publish_assets (CDN).

The voice, sound and visual vendors sit behind internal interfaces (TtsProvider, SoundProvider, VisualProvider) so they can be swapped. The vendor choice is open (§11). Higgsfield is connected to our workspace as a candidate for generated visuals and audio, to be evaluated. The prod web player renders visuals from parameters today, so the API needs nothing more for prod v1/v2.

8.5 Journey intelligence

  • Check-in → next chapter. Code picks the direction from the mood: 1–2 = gentler, 3 = keep, 4–5 = keep what worked and go a little deeper. It also picks the unlock time: tomorrow, or tomorrow night for sleep. The model (chapter.plan) writes the sentence and selects up to 3 allowed changes consistent with the direction. The result is the prod v2 "Chapter 2 keeps what worked and goes a little deeper." Prod v1 shows only the headline and the reminder.
  • Progress in words. trend and usual are computed as in feelingSummary. The model writes headline/detail from them, under a rule: no percentages, no projections, no clinical words. The result is cached per check-in. Two-week reports are generated by a scheduled job in batch.

8.6 Voice input

/uploads/voice transcribes server-side with a speech-to-text vendor (open, §11). The transcript becomes the message text. The audio is deleted after transcription unless the user keeps voice notes. vercel.json currently blocks the microphone (Permissions-Policy); that must change before launch (O14).

8.7 Safety (mandatory)

  • Where it runs: safety.classify on every user-authored text before any other route: messages, voice transcripts, check-in notes, journal, publish fields.
  • When it flags crisis/self_harm (severity ≥ medium):
    • generation pauses for that turn;
    • the assistant returns the scripted support message, with local crisis resources by locale (problem.code: unsafe_content for non-chat inputs; in chat, a message.completed with safety.flagged: true and a support card);
    • a moderation item is created for a human. Aurelia never "treats".
  • Content rules for every generative route: no medical claims, no diagnosis, no numeric health promises (decision 13), no spiritual/frequency claims when the person excluded them.
  • Moderation: published content passes moderation.publish. User reports go to /admin/moderation.
  • Required before launch: a written safety policy with clinical and legal review (logic H1–H3). This contract only provides the hooks.

8.8 Quality, evals and cost

  • Evals per route before launch, rerun on every policy change:
    • golden conversations from the six personas and the three interviews;
    • "honours no …" checks;
    • "no invented numbers" checks;
    • schema validity;
    • basis faithfulness.
  • 👍/👎 feedback (…/feedback) and the checkin_answered event feed the eval sets.
  • AI monitoring (/admin/ai/metrics) tracks, per route: tokens, cost, latency, refusals, fallbacks, safety flags and eval score.
  • Budgets: a hard per-user daily AI cost ceiling (alerts at 80 %), the plan's build limit, and per-route max_tokens. Cost per completed core loop (onboard → first chapter played → check-in) is the headline metric, not cost per request.
